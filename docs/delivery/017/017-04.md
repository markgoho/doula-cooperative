## Hugo Naming Conventions and Best Practices

> For the authoritative, detailed architecture and structure guide, see: [hugo/DIRECTORY_STRUCTURE.md](../../../hugo/DIRECTORY_STRUCTURE.md)

### File & Folder Naming Conventions

- **General:**
  - Use lowercase and hyphens for file and folder names (e.g., `about-doulas/`, `birth-support.md`).
  - Avoid spaces and underscores in names.
  - Use clear, descriptive names for all files and directories.

- **Content:**
  - Section index files: `_index.md` (for section landing pages)
  - Page bundles: `index.md` inside a folder (e.g., `about/index.md`)
  - Individual content: `{slug}.md` (e.g., `jane-doe.md` for a doula profile)

- **Layouts:**
  - Use Hugo conventions: `baseof.html`, `list.html`, `single.html` in `layouts/_default/`
  - Partials: descriptive names (e.g., `header.html`, `footer.html`, `meta.html` in `layouts/partials/`)

- **Assets:**
  - SCSS: use meaningful names (e.g., `styles.scss`, `non-critical.scss`)
  - SCSS partials (if used): prefix with underscore (e.g., `_variables.scss`, `_mixins.scss`)
  - Images: descriptive, lowercase, hyphenated (e.g., `doula-group-photo.jpg`)

- **Data:**
  - Use YAML for readability (e.g., `navigation.yaml`, `board.yaml`)
  - Name files after their purpose (e.g., `doulas.yaml` for doula data)

- **Configuration:**
  - Main config: `hugo.toml` at project root
  - For complex sites, consider `config/_default/hugo.toml` (not currently used)

### Best Practices for Hugo Development

1. **Backlog-Driven Structure:**
   - Only create folders/files that match the structure defined in the product backlog and [hugo/DIRECTORY_STRUCTURE.md](../../../hugo/DIRECTORY_STRUCTURE.md).
   - Avoid generic sections (e.g., `posts/`, `services/`) unless required by a PBI.

2. **Content Organization:**
   - Organize all site content under `content/` by type and section.
   - Use `_index.md` for section landing pages and `index.md` for page bundles.

3. **Template Modularity:**
   - Use partials for reusable template components (e.g., header, footer, meta tags).
   - Keep templates in `layouts/_default/` and `layouts/partials/`.

4. **SCSS/CSS Organization:**
   - Place all processable styles in `assets/scss/`.
   - Use a main entry point (e.g., `styles.scss`) and separate non-critical styles (e.g., `non-critical.scss`).
   - For larger projects, use SCSS partials (e.g., `_variables.scss`, `_mixins.scss`, `_base.scss`).

5. **Data Separation:**
   - Use `data/` for frequently changing or structured data (e.g., navigation, team, doulas).
   - Reference data files in templates for dynamic content.

6. **Static Assets:**
   - Place unprocessed files (images, fonts, favicon, robots.txt) in `static/`.
   - Structure `static/` to mirror desired output URLs.

7. **Version Control:**
   - Do not version `public/` or `resources/` (build/cache output).
   - Use `.gitkeep` to track empty directories if needed.

8. **Documentation:**
   - Keep `hugo/DIRECTORY_STRUCTURE.md` up to date as the single source of truth for structure and conventions.
   - Link to this doc from other relevant documentation.
